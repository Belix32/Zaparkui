# Next steps для Zaparkui

## 1. Применить SQL-миграции

Примените миграцию `supabase/migrations/006_security_hardening.sql` в целевом Supabase-проекте после проверки на staging. Она добавляет server-side helper для проверки администратора, защищающий trigger для системных полей профиля и безопасные RLS-политики обновления профиля. После применения проверьте, что обычный пользователь может менять только пользовательские поля, а изменение `role`, `is_blocked`, `auth_id`, `id` и `created_at` отклоняется.

## 2. Завершить серверную YooKassa-интеграцию

Файл `supabase/functions/create-yookassa-payment/index.ts` сейчас является намеренной заглушкой. Реализуйте в нём операции создания и проверки платежа через YooKassa SDK/API. Секрет должен храниться только в Supabase Edge Function Secrets под именем `YOOKASSA_SECRET_KEY`; идентификатор магазина также должен быть серверной переменной. Не используйте префикс `VITE_` для секретных значений и проверьте production browser bundle на отсутствие секретов.

## 3. Проверить платёжный и booking-flow на staging

Проверьте сценарии создания бронирования, проверки пересекающихся интервалов, отмены и повторной оплаты. Отдельно проверьте границы интервалов: запрос должен считаться конфликтующим, если существующий интервал удовлетворяет одновременно условиям `existing.end_date >= requested.start_date` и `existing.start_date <= requested.end_date`. Ошибка запроса доступности должна блокировать бронирование, а не разрешать его.

## 4. Выполнить регрессионное тестирование

Проверьте вход, регистрацию, профиль, каталог парковок, избранное, отзывы, административные страницы, загрузку изображений и баннеры promotions. Убедитесь, что удалённые маршруты `/travel`, `/admin/travel` и `/partner` больше не доступны, а lazy-loaded chunks для travel-компонентов не появляются в production build.

## 5. Настроить окружение и деплой

Перед деплоем задайте только публичные переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` во frontend-окружении. Секреты YooKassa добавьте исключительно в Supabase Edge Function Secrets. После публикации ветки создайте Pull Request, примените миграцию на staging, выполните smoke-test и только затем направьте изменения в production через Vercel.

## 6. Контроль качества

Выполните `npm ci` и `npm run build` в CI. Рекомендуется добавить автоматические тесты для RLS-политик профилей, availability-функции и проверки отсутствия строк `VITE_YOOKASSA_SECRET_KEY`, `api.yookassa.ru` и travel-маршрутов в browser bundle. После установки зависимостей текущий `npm audit` сообщает о найденных уязвимостях; их следует отдельно разобрать и обновлять зависимости с учётом совместимости проекта, не применяя `npm audit fix --force` без проверки.
